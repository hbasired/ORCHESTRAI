# OPEN GAPS LEDGER — carry-forward register of unresolved gaps, vulnerabilities & problems

> **Purpose (operator mandate, 2026-05-31).** Not every gap an audit finds can be fixed in the stage where it
> is observed — many are legitimately solved by a *later* stage's implementation. This ledger records those
> gaps with the **target stage** that will fix them, so that when that stage is implemented the system already
> knows the earlier-observed gap and **folds its fix into that stage's work**. Nothing observed is lost.

## How this ledger is used (protocol)

1. **Append (independent audit / CTO review / any session).** When a gap cannot be fixed now, add a row with a
   `target_stage`. The independent `task-auditor` and `cto-reviewer` MUST append their deferred findings here
   (in addition to their report). CTO `remediation_map.json` entries are also reflected here.
2. **Surface (stage start).** `scripts/start-task.sh <stage>` and `/begin` surface every OPEN row whose
   `target_stage` ≤ the stage being started, so the implementer pulls the fix into the task doc's acceptance
   criteria. (CTO future-task remediations are additionally auto-appended to the named task doc by
   `scripts/generate-remediation-tasks.sh`.)
3. **Resolve (stage close).** When a stage fixes a gap, set its `status` to `RESOLVED (Stage NN, YYYY-MM-DD)`.
   `close-task.sh` should warn if OPEN rows targeted at the just-closed stage remain unresolved.
4. **Append-only history.** Do not delete rows — mark `RESOLVED` / `WONTFIX (reason)`. Mirrors KB strikethrough discipline.

Severity: `critical` (safety/security/blocking) · `high` · `medium` · `low`.
