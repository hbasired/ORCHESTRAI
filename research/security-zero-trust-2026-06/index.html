MCP Security & Zero-Trust Posture — an Honest Assessment

2026-06-15 · research §20 · KB_16 · operator-requested. No reassurance theatre: what's secured by construction, what is NOT yet built, and the staged plan. Frameworks: CSA Agentic Trust Framework · NIST SP 800-207 · OWASP Top-10 for Agentic Apps · IBM Agentic Trust blueprint.

1. Is the MCP architecture we shipped secure?

Short answer: secure for what it currently is (a local, in-process tool surface) — and deliberately NOT yet hardened for the network/multi-party case, because that case doesn't exist until Stage 14.

The documented MCP threats in 2026 are tool poisoning (malicious instructions hidden in tool descriptions), schema poisoning, prompt injection via tool I/O, and credential-aggregation token theft (one rogue server leaking OAuth tokens). By construction, none of these are reachable today:

MCP threatReachable here?Why
Tool poisoning from a rogue/remote serverNoservers are OUR code, spawned as local stdio subprocesses — no registry discovery, no third-party server
OAuth-token aggregation theftNono OAuth tokens aggregated; no network listener
Network MITMNostdio over the local process tree, not a socket
Prompt injection via tool descriptions read by an LLMNothe self-healing loop is LLM-free; tools are wired by us, not read by a model from untrusted metadata

3. Are we employing Zero-Trust for the agentic system?

Partially — by design — and we can (and will) make it a coherent, named architecture. The four ZT principles, mapped honestly to what is SHIPPED:

ZT principleWhat we shipThe gap
Verify explicitlyHITL interrupt() on SIL-1+; neuro-symbolic plan verifier gates execution against a binding PlantStateno per-call agent identity auth yet
Least privilegeMem0 namespace isolation; no-LLM-direct-actuator (all via safety/validator); A2A exposes a deliberate capability subsetMCP tools not capability-scoped; DB role not least-privilege-split
Assume breachappend-only hash-chained audit; immutability triggers; PQC migration (13.5/18)no per-agent ZTNA network segmentation
Continuously validateevery decision audited + traced; verify_range integrityno continuous behavioural anomaly detection on agents

Why not fully zero-trust yet? A coherent ZT layer needs the PQC identity primitives (Stage 13.5), the A2A identity/mTLS boundary (Stage 14), the functional-safety wrapper (Stage 17), and the red-team eval harness (Stage 20) — all already on the roadmap. Bolting a half ZT layer on before those exist would be theatre, which our rules forbid. Can we? Yes — gap G-064: adopt the CSA Agentic Trust Framework + NIST 800-207 as the named target, give every agent/tool a non-human ML-DSA-65 identity (already specced in KB_16), scope MCP tools to capabilities, and add OWASP-Agentic evals.
