1. Why & what

Stage 12 wrote the audit_chain with a clearly-labelled placeholder signature, to be replaced here. Stage 13.5 wires real FIPS-204 ML-DSA-65 (the NIST post-quantum signature standard) behind a pluggable KeyProvider boundary — so the EU-AI-Act audit chain + every ADR now carry genuine post-quantum signatures, and buying a hardware HSM later is a config change, not a code change.

audit_chain.append(hash) ─→ pqc_signing.sign ─→ get_key_provider() ─→ SoftwareKeyProvider (dilithium-py ML-DSA-65) └→ Pkcs11Provider (HSM) ┐ swap by └→ VaultProvider ┘ CRYPTO_PROVIDER

Honest caveat: dilithium-py is not side-channel-hardened (the author says so). That's acceptable because it is the dev/no-budget software tier — production swaps to pkcs11(HSM)/ vault via CRYPTO_PROVIDER, where signing runs in hardened hardware. The whole point of the KeyProvider abstraction (KB_13 §v2.1.5) is that this swap is config-only.

3. What was built

  • crypto/key_provider.py — the KeyProvider ABC + get_key_provider() factory (software | pkcs11 | vault). No caller imports a concrete backend.
  • crypto/software_provider.py — real ML-DSA-65 (dilithium-py) + a versioned filesystem keystore (overlap rotation + historical verification).
  • crypto/pkcs11_provider.py / vault_provider.py — honest stubs (raise with guidance; full impl + the software→pkcs11 swap drill = Stage 22 pilot). Never a faked HSM signature (Rule 1a).
  • crypto/pqc_signing.py + key_manager.py + hmac_sha384.py (OT MAC, Stage 15).
  • audit_chain now real-signed (ML-DSA-65, key_version≥1) — the Stage-12 _sign() already hooked crypto.pqc_signing, so it needed no change. scripts/sign-decision-log.py signs ADRs with real ML-DSA-65; all decision-logs batch re-signed.
  • No RSA/ECDSA/EdDSA in backend/crypto/ — the pre_tool_use hook + a new pqc-crypto-tests CI grep enforce it.
