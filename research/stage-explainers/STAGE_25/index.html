2. What the load test CAUGHT (why load tests exist)

The first run of the G-066 load test found two real defects — both fixed and re-proven:

  • defect 1 Worker-thread import-lock deadlock: 6 threads simultaneously triggering the runtime's lazy in-function model imports deadlocked on Python's import lock (the SAME class as the Stage-11.5 FastMCP stdio deadlock). Fix: warm-first — the first incident runs synchronously in the calling thread (all heavy imports/model loads resolve once), only the remainder fan out; plus a per-future timeout so a stuck run fails LOUDLY.
  • defect 2 Sequential re-processing: the advisory lock prevents CONCURRENT double-runs but a late duplicate re-acquired the lock after the first run completed and re-processed the incident. Fix: an at-most-once ledger (incident_processed PK table; claim inserted under the lock before the run; failed runs release the claim so retry stays possible).
  • also a mid-test HuggingFace revision-check went to network and stalled — load tests now run HF_HUB_OFFLINE=1 hermetic.
