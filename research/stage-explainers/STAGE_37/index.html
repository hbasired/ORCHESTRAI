Stage 37 — Bidirectional CDC → diagnose the induced problem → self-optimize BUILD INCREMENT

Edit a value in the factory database and the system now REASONS about the problem that edit causes — it diagnoses the root cause and drives the self-healing loop, instead of replaying a canned incident. Closes ledger gap G-024 (open since 2026-05-31 — the operator's original product vision). 2026-07-18 · research §48.

Stage 13 made database changes flow INTO the agent (an incident row or a status flip → a pre-formed inject). Stage 37 closes the loop the other way: change any operational value — a stage's defect rate, an inventory level, a supplier's reliability — and a new DB trigger emits the diff, the backend diagnoses the induced problem (defect surge? bottleneck? energy anomaly? stockout?), and that diagnosed problem enters the same validator-gated self-healing loop. The reasoner proposes; it never actuates (Hard Rule 3 intact).

Why now

The build is theatre-free and the CTO-#6 in-house items are all paid. The operator chose to keep closing the genuine remaining free/local ledger gaps before the consolidated handoff. G-024 — "edit a DB value → CDC detects → engine reasons about the induced problem → self-optimize" — is the highest-value of those and was the operator's original product idea. It builds directly on the Stage-13 CDC and the Stage-11 self-healing runtime; nothing new had to be invented, only the reverse direction wired and a diagnosis layer added.

How it works (real file paths)

  • The value-change trigger — backend/alembic/versions/0010_cdc_value_changes.py. A cdc_emit_value() plpgsql function + three AFTER UPDATE OF <value columns> triggers on stages (defect_rate / throughput / energy_consumption_kw / utilization), inventory (current_stock / days_of_supply), suppliers (reliability_score / lead_time_days). On a monitored change it writes {table, column, old, new, target_id} into the existing Stage-13 cdc_outbox and fires pg_notify('cdc_events', …) — reusing the durable outbox + NOTIFY + drain machinery.
  • The root-cause reasoner — backend/ingestion/cdc_reasoner.py. diagnose_change() is a pure, unit-testable function: a value edit → a root-cause-labelled InducedProblem whose severity is derived from the edit magnitude, or None for a benign edit (an honest "no problem", never a fabricated one).
  • The listener routing — backend/ingestion/cdc_listener.py. change_to_inject now checks the value-edit branch first (keyed on the column field) so value rows reach the reasoner instead of being swallowed by the status branch — a subtle ordering bug caught during live testing and pinned by a regression test.
  • The closed loop — process_value_edit() diagnoses → signs the reasoning to the audit_chain (cdc.diagnose, EU-AI-Act Art-12) → optionally drives run_incident() (the validator-gated LangGraph loop). Surface: POST /factory/db-edit in backend/api/conversation_routes.py.

Honesty (Rule 1a)

  • Benign edits diagnose nothing. A small change, an improvement, or an unmonitored column returns None / diagnosed=False. Inventory without a reorder_point context is benign — we do not fabricate a stockout without the threshold.
  • Severity is magnitude-derived, never a hardcoded constant.
  • Hard Rule 3 preserved. The reasoner adds no new actuator.* emitter; the diagnosed problem enters the same validator-gated loop; the sole actuator emitter remains master.dispatch_order.
  • Honest scope. This is a documented-threshold diagnostic rule engine, not a learned causal model. Deeper learned causal discovery over real edit→outcome traces needs pilot data (G-035, buyer-blocked) — deferred, not overclaimed.

What changed in the system

  • The CDC loop is now bidirectional: DB → agent (Stage 13) AND operator-DB-edit → diagnosis → self-heal (Stage 37).
  • New endpoint POST /factory/db-edit; new signed audit event type cdc.diagnose.
